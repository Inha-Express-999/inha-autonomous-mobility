## 1. 실험 목적과 범위

Python 서버의 기본 동작을 확인하고, 다음 네 알고리즘 쌍을 동일 입력 조건에서 비교한다.

| 구분 | 기준 알고리즘 | 비교 알고리즘 | 확인할 내용 |
|---|---|---|---|
| E1 전역 경로 | Dijkstra | A* | 경로 비용 일치, 탐색량, 계산시간, Open Set 크기 |
| E2 배차 | Greedy | Hungarian | 배정 결과, 총비용, 공차거리, 계산시간 |
| E3 동적 재탐색 | A* 전체 재탐색 | D* Lite | 비용·도달 가능 판정 일치, 재탐색 시간, 경로 변경 |
| E4 차량 경로 조정 | 우선순위 예약 | CBS / Disjoint CBS | 계획 성공률, 계획상 충돌, 완료시간, 대기시간, 계산시간 |

모든 실험은 합성 지도·비용·차량 조건에서 수행했다. 이 보고서는 실제 캠퍼스 운송 성능, 실제 차량 안전 또는 전체 시스템의 구현 완료를 입증하지 않는다. 개선 알고리즘이 모든 지표에서 우수하다고 가정하지 않고, 효과와 계산비용을 함께 평가한다.

µs는 마이크로초, ms는 밀리초다. 원자료의 ns를 각각 1,000 또는 1,000,000으로 나누었다. p50은 중앙값에 해당하며, p95는 측정값의 95%가 그 값 이내인 지점이다. 경로 비교 도구는 nearest-rank 방식의 분위수를 사용한다.

반복 실행은 같은 입력의 결과 안정성과 실행시간 분포를 확인한다. 서로 다른 20개 지도·seed를 평가한 것으로 해석하지 않는다. 각 실행 출력에 커밋·장비·실행 시각이 모두 포함된 것은 아니므로, 위 커밋은 보고서 작성 시 확인한 기준 코드이며 실행별 소스 해시 증빙은 추가 보완이 필요하다.

## 4. E1 — Dijkstra와 A* 전역 경로 비교

### 4.1 일반 조건의 반복 비교

11개 지점의 서로 다른 출발·도착 조합 110개를 대상으로, 워밍업 2회 후 20회 측정했다. 알고리즘별 측정 표본은 2,200개다.

| 지표 | Dijkstra | A* |
|---|---:|---:|
| 도달 가능한 조합 | 110/110 | 110/110 |
| 서로 같은 경로 비용 | 110/110 | 110/110 |
| 반복별 비용·도달 판정 일치 | 20/20 | 20/20 |
| 평균 확장 노드 수 | 5.500 | 2.827 |
| 평균 계산시간 | 9.786µs | 6.877µs |
| 계산시간 p50 | 9.900µs | 6.100µs |
| 계산시간 p95 | 15.700µs | 13.700µs |
| 경로별 Open Set 최대 크기의 평균 | 5.609 | 4.791 |

확장 노드와 Open Set 지표는 출력의 첫 측정 반복에 해당하는 경로별 기록을 요약했고, 시간 지표는 전체 2,200개 표본을 사용했다.

A*는 97개 조합에서 더 적은 노드를 확장했고, 13개에서는 같았으며 더 많이 확장한 조합은 없었다. 평균 확장 노드는 약 **48.6%**, 평균 계산시간은 약 **29.7%** 감소했다. 이번 지도에서 Dijkstra와 동일한 경로 비용을 유지하며 탐색량을 줄였다는 결과다. 동일 비용 경로가 여럿이면 노드열 자체는 달라도 되므로 비용 일치와 경로 모양 일치를 구분한다.

### 4.2 이동지원 조건 실험의 대조 확인

같은 11개 지점 지도에 `--require-step-free`를 적용한 결과도 비용 일치 110/110, 반복 일치 20/20이었다. 평균 확장 노드는 5.500/2.827, 평균 시간은 10.010/6.924µs였다.

그러나 이 지도는 **34개 간선 모두 `step_free: true`**다. 제외되는 도로가 없어 일반 조건과 경로 및 비용이 동일했으므로, 이 실행은 접근성 제약에 의한 우회를 증명하지 않는다. 실행 간 미세한 시간 차이를 이동지원 조건의 성능 영향으로 해석하지 않는다.

### 4.3 실제 제약이 있는 합성 지도에서의 우회 확인

6개 지점 지도에서 Stop 2 → Stop 5를 비교했다. 직접 연결인 `e25`는 `step_free: false`다.

| 지표 | 일반 조건 | 이동지원 조건 |
|---|---|---|
| 경로 | 2 → 5 | 2 → 3 → 4 → 6 → 5 |
| 경로 거리 | 120m | 490m |
| 경로 비용 | 24초 | 188초 |
| Dijkstra/A* 비용 일치 | 일치 | 일치 |
| 확장 노드(Dijkstra/A*) | 2 / 1 | 5 / 5 |

양 알고리즘 모두 이동지원 조건에서 `e25`를 제외하고 우회했다. 비용은 `거리/허용속도 + 혼잡 + 구역 + 예상대기 페널티`이며 실제 경과시간이 아니다. 각 조건을 한 번만 실행했으므로 이 우회 사례의 실행시간은 성능 비교 근거로 사용하지 않는다. 이 결과는 합성 간선의 접근성 필터 검증이며 실제 시설 접근성 승인이 아니다.

## 5. E2 — Greedy와 Hungarian 배차 비교

### 5.1 고정 비용행렬 비교

차량 3대, 요청 3개, 배정 불가능한 조합 3개를 사용했다. 동일 비용표에서 워밍업 2회 후 20회 반복했다. 비용표의 `null` 조합은 배정 대상에서 제외한다.

| 요청 | Greedy 배정 / 비용 | Hungarian 배정 / 비용 |
|---|---|---|
| R-MOBILITY | V01 / 1.0 | V02 / 2.0 |
| R-PASSENGER | V02 / 100.0 | V01 / 1.1 |
| R-CARGO | V03 / 3.0 | V03 / 3.0 |

| 지표 | Greedy | Hungarian |
|---|---:|---:|
| 배정 수 | 3 | 3 |
| 총비용(초 단위 합성 비용) | 104.0 | 6.1 |
| 평균 계산시간 | 2.505µs | 8.870µs |
| 계산시간 p95 | 3.100µs | 10.300µs |
| 반복 배정 결과 | 동일 | 동일 |

Hungarian은 전체 조합을 고려하여 총비용을 약 **94.1%** 줄였지만 평균 계산시간은 약 **3.54배**였다. Greedy가 첫 요청에 V01을 사용하면 두 번째 요청에 비싼 V02가 남는 비용표이므로, 이 결과를 일반적인 배차 개선율로 해석하지 않는다. 이 실험은 배정 계산 자체의 비교이며 에너지 모델은 포함되지 않았다.

### 5.2 합성 경로 비용을 사용한 배차 비교

사용자가 전달한 출력은 전체 결과 중 요약 두 행과 비용식·한계 설명이다. **case 이름과 전체 case별 결과가 없어 아래 수치를 특정 시나리오 이름이나 전체 실험의 합계로 확정하지 않는다.** 실행 명령은 20회 반복이지만 전달된 부분만으로 case별 원자료와 표본 수를 독립 확인할 수 없다.

| 지표 | Greedy | Hungarian | 상대 변화 |
|---|---:|---:|---:|
| 배정 수 | 3 | 3 | 같음 |
| 총비용 | 245.0 | 126.0 | 48.6% 감소 |
| 공차거리 | 760m | 250m | 67.1% 감소 |
| 계산시간 p50 | 0.8144ms | 0.8001ms | 비슷함 |
| 계산시간 p95 | 0.9981ms | 0.8718ms | 이번 실행에서 감소 |
| 반복 배정 결과 | 동일 | 동일 | — |

비용식은 `pickup_s + 0.5 × trip_s + 2 × lateness_s`다. 단위가 초여도 가중합 비용이므로 전체 운송 완료시간으로 해석하지 않는다. 두 방식은 동일한 초기 캐시 상태에서 시작한다. 시간 측정에는 후보 생성, 우선순위·매칭, 픽업 경로 설치가 포함되고 시나리오 구성·복사·증거 경로 추적은 제외된다.

이 비교에는 실제 서비스 코드의 우선순위·공정성·batch 선택 정책이 포함된다. Hungarian 결과를 모든 요청에 대한 무제약 전역 최적해로 표현하지 않는다. 에너지·충전·희소 차량 페널티·완료 이력 기반 작업량 공정성은 이 실험에 포함되지 않는다. 개별 Pickup ETA, 요청 대기시간, 총 이동거리의 전체 결과는 제공되지 않아 별도로 평가하지 않았다.

## 6. E3 — A* 전체 재탐색과 D* Lite

11개 노드 합성 그래프에서 seed 17로 생성한 비용 변경·도로 폐쇄/재개·출발점 이동 이벤트 30개를 20회 반복했다. 총 600개 이벤트 처리에서 Dijkstra를 정답 비교 기준으로 사용했다.

- 지도 SHA-256: `fbb59107aefcf53d67ae221c796020b56e450171d49ea1903b59c2775d95cfa6`
- 시간은 계약 검증과 초기 D* Lite 생성까지 포함한 함수 호출 단위다. 워밍업은 없다.

| 지표 | A* 전체 재탐색 | D* Lite |
|---|---:|---:|
| Dijkstra 비용·경로 없음 판정과 일치 | 전체 일치 | 전체 일치 |
| 재탐색 시간 p50 | 29.2µs | 70.1µs |
| 재탐색 시간 p95 | 39.0µs | 123.1µs |
| 알려진 확장 노드 합계 | 1,860 | 1,700 |
| 기록된 갱신 노드 합계 | 해당 지표 없음 | 10,140 |
| 경로 변경 횟수 | 400 | 400 |
| 경로 없음 판정 | 140 | 140 |

노드 합계와 경로 변경 수는 20회 반복을 합친 값이다. A*는 경로가 없는 경우의 확장 노드 수를 기록하지 않아 두 알고리즘의 총 탐색량을 직접 비교하거나 감소율을 산출할 수 없다. 출력에서 A* 갱신 노드 합계 0도 동등한 갱신 지표가 구현되어 있다는 의미가 아니다.

D* Lite의 중앙값은 A*의 약 **2.40배**, p95는 약 **3.16배**였다. 이 작은 그래프와 이벤트 조건에서는 A*가 더 빨랐다. 갱신·상태 관리 비용이 재사용 이득보다 컸을 가능성이 있지만 원인을 분리 측정하지는 않았다. 더 큰 지도, 국소 비용 변경, 초기 생성 비용을 분리한 추가 실험이 필요하다.

`cost_s: null`은 경로 없음 판정이다. 모든 도로를 제외한 이벤트가 포함되어 있어 이 값을 곧바로 알고리즘 오류로 취급하지 않는다. CPU 시간은 원자료에 있으나 일부 이벤트에서 0으로 기록되어 작은 호출의 속도 판단에는 wall time을 우선했다.

## 7. E4 — 우선순위 예약, CBS, Disjoint CBS

차량 3대의 합성 경로를 2초 단위 시간 슬롯으로 모델링했다. 자원 통과 여유는 2초, 정상 계획 범위는 30슬롯(60초), 짧은 계획 범위는 3슬롯(6초)다. 각 사례·알고리즘을 5회 실행했다. 설정상 탐색 제한은 constraint-tree 노드 2,000개와 low-level 확장 50,000개다.

### 7.1 정상·역순 우선순위 시나리오

| 사례 | 알고리즘 | 성공 | 계산 p50(ms) | 계산 p95(ms) | Makespan(초) | 도착시간 합(초) | 대기시간 합(초) |
|---|---|---:|---:|---:|---:|---:|---:|
| mixed-three | 우선순위 예약 | 5/5 | 2.583 | 3.261 | 54 | 104 | 40 |
| mixed-three | 기본 CBS | 0/5 | 1,702.376 | 1,709.535 | — | — | — |
| mixed-three | Disjoint CBS | 5/5 | 798.704 | 811.345 | 48 | 94 | 42 |
| reverse-priority | 우선순위 예약 | 5/5 | 2.716 | 2.850 | 56 | 114 | 50 |
| reverse-priority | 기본 CBS | 0/5 | 1,661.474 | 1,730.911 | — | — | — |
| reverse-priority | Disjoint CBS | 5/5 | 803.547 | 809.020 | 48 | 94 | 42 |

Makespan은 모든 차량이 도착할 때까지의 계획시간이다. 도착시간 합과 대기시간 합은 별도 지표이며 총 경로 거리와 동일하지 않다. 각 성공 그룹의 계획 지표는 5회 반복에서 동일했다.

성공한 우선순위 예약과 Disjoint CBS의 **계획상 충돌 토큰 수는 모두 0**이었다. 기본 CBS는 두 사례 모두 `BUDGET_EXCEEDED`, 사유 `constraint_tree`로 종료했다. 이는 주어진 탐색 한도에서 해를 반환하지 못했다는 뜻이며 경로 자체가 존재하지 않는다는 뜻은 아니다. 표의 기본 CBS 시간은 성공 계획의 계산시간이 아니라 한도 초과까지의 시간이다.

일반 사례에서 Disjoint CBS는 Makespan을 54초에서 48초로 약 **11.1%** 줄이고 도착시간 합을 104초에서 94초로 줄였다. 반면 대기시간 합은 40초에서 42초로 증가했고, 계산 중앙값은 약 2.6ms에서 약 799ms로 늘었다. 우선순위를 반대로 둔 사례에서는 예약 방식의 Makespan이 56초였고 Disjoint CBS는 48초로 약 **14.3%** 짧았다. 모든 지표가 동시에 개선된 결과는 아니다.

### 7.2 계획시간 부족 시나리오

`insufficient-horizon`에서 세 방식 모두 0/5 성공이었다. 우선순위 예약은 `PRIORITY_ORDER_FAILED`, 두 CBS 방식은 `NO_SOLUTION_WITHIN_HORIZON`을 반환했다. 설정된 시간 범위에서 개별 운송을 완료할 수 없는 사례이며, 정상 계획과 실패 사례를 함께 평가했다.

### 7.3 적용 범위

비교 대상 Priority는 오프라인 고정 순서 예약이며 실시간 `ResourceReservations` 관리자 자체가 아니다. 계산시간은 solve 호출을 측정하며 입력 검증과 Dijkstra 전처리는 별도다. 원자료에서 `physical_conflicts: null`, `executable: false`이므로 실제 Unity 충돌 0 또는 실시간 주행 적용 성공으로 표현하지 않는다. 연속 차체 형상, 센서 지연, 실제 자원 임대 만료와 교착 복구는 이번 평가 범위 밖이다.

## 8. 종합 해석과 다음 작업

| 실험 | 이번에 확인한 결과 | 남은 확인 |
|---|---|---|
| E1 | 동일 비용을 유지하며 A* 평균 확장량 48.6% 감소; 합성 이동지원 불가 간선 우회 | 더 큰 지도·실제 승인 그래프, 통행 불가능 사례의 폭넓은 검증 |
| E2 | 고정 비용표 및 전달된 경로 기반 요약에서 Hungarian 비용 감소 | 경로 기반 전체 case 원자료, 실제 대기·완료·에너지·공정성 지표 |
| E3 | 두 방식의 비용·도달 판정 일치; 이번 조건에서는 A*가 빠름 | A* 실패 탐색량 계측, 큰 그래프·국소 변경, 초기 비용 분리 |
| E4 | 예약은 빠름; Disjoint CBS는 계획 완료시간 개선; 기본 CBS는 한도 초과 | 탐색 규모·한도 변화, 더 다양한 사례, Unity 실행·실제 충돌 검증 |

네 가지 합성 비교를 한 차례 재현했으며, 전체 E1~E4 또는 프로젝트 완료 조건을 모두 충족한 것은 아니다. 후속 작업의 우선순위는 다음과 같다.

1. 경로 기반 배차의 전체 출력과 case 이름을 확보하고, 실행별 날짜·소스 커밋·장비 정보를 원자료와 함께 보관한다.
2. Unity 담당자와 동일 버전에서 WebSocket 요청/상태·위치·완료를 확인하고, 서버 결과와 화면의 일치 및 연결 중단/복구를 기록한다.
3. 큰 그래프·추가 seed·다양한 요청/폐쇄/충돌 조건으로 일반성을 평가한다. 동일 입력 반복과 독립 시나리오 반복을 구분한다.
4. 실패·누락 계측을 보완하고, 개선 효과와 계산비용이 확인된 범위에 맞춰 알고리즘 적용 조건을 정한다.

발표용 핵심 문장: **합성 환경에서 기준 알고리즘과 비교 알고리즘을 재현했고, A*와 Hungarian의 이점뿐 아니라 D* Lite의 계산 오버헤드와 CBS의 탐색 한계도 확인했다. 알고리즘 선택은 문제 규모와 제약, 계획 품질과 계산시간의 균형에 따라 결정해야 한다.**

python -m campus_sim.cli route-compare --map maps/fixtures/campus-synthetic-6.json --start-stop fixture_stop_2 --goal-stop fixture_stop_5 --require-step-free
