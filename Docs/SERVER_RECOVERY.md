# Python 물리 운송 상태 저장·복원

SQLite checkpoint를 명시적으로 켜면 요청, command_id 응답 기록, 배정 차량/운송 단계, 배터리 잔량, 배차 순서/이벤트를 하나의 transaction으로 저장한다. 요청 응답과 운송 단계 갱신을 내보내기 전에 저장하며 실패 시 해당 서버는 새 제어 명령을 중단한다. Python 서버 재기동 자체는 별도 실행 주체가 담당한다.

## 활성화

저장소 루트에서 실행한다. 하나의 DB는 동시에 하나의 서버만 사용해야 한다. 기존 서버가 있으면 동일 포트에 중복 실행하지 않는다.

```powershell
.venv/Scripts/python.exe -m campus_sim.desktop_server --host 127.0.0.1 --port 8765 --state-db tmp/physical-service.db
```

Unity PC_Bootstrap은 호환되는 실행 중 서버를 재사용한다. Unity가 서버를 직접 실행하게 하려면 Unity/Hub 실행 전에 `CAMPUS_SIM_RECOVERY_DB` 환경변수에 전용 DB의 절대 경로를 지정할 수 있다. 설정하지 않으면 기존 메모리 전용 동작이다. 기본값을 바꾸지 않아 기존 합성 웹 실험/초기화 흐름에 데이터를 섞지 않는다.

같은 DB로 재시작하면 새 run ID를 발급하고 이전 요청·배차·단계를 복원한다. 차량 연결 토큰, 센서 관측, 경로/조향 명령, 단조 시계, 에너지 거리 누적의 직전 위치는 복원하지 않는다. 신선한 차량 관측을 받기 전에는 배차/경로 재개를 하지 않으며, 관측 이후 같은 단계의 목적지로 새 mission을 생성한다. 승하차 대기 시간은 안전하게 다시 시작하고, 서버가 꺼진 시간을 운송/충전 시간으로 계산하지 않는다. 완료된 요청은 완료로 보존한다.

지도 geometry, 차로 profile, 도로 비용, 거점 연결, 차량 능력, 배터리 정책 및 저장 schema가 맞지 않거나 checksum/DB가 손상되면 빈 서비스로 시작하지 않고 실패한다. 원본 DB는 보존한다. 저장 실패도 서버 재시작 전까지 오류 상태를 유지한다.

## 범위와 운영 시 주의

- 물리 운송 전용이다. 이 모드의 접수는 차량이 아직 연결되지 않아도 가상 운송으로 전환하지 않는다. 합성 scenario 생성은 사용할 수 없다.
- 일반 `/v1/requests` fixture 서비스, 수동 목적지 mission, 합성 VirtualTrip, 충전 세션 과거 이력 전체의 복원 기능은 아니다.
- 한 서버/단일 worker만 사용한다. 여러 프로세스의 동시 DB 소유·조정은 지원하지 않는다.
- 명시적인 `/v1/demo/reset`은 DB에도 새 빈 상태를 저장한다. 정상 종료/재시작과 초기화는 다르다.
- 자동 서버 재기동, 관제 전용 복구 화면, DB 이전/백업 UI는 아직 추가하지 않았다. 새 연결 준비 전에는 기존 관제의 차량 표시와 요청 상태를 함께 확인한다.
- 매 물리 배차 step의 동기 SQLite 저장은 I/O 비용이 있다. 현재 소규모 기능 검증 범위이며 다중 차량/느린 디스크 성능은 별도 측정이 필요하다.

## 검증
