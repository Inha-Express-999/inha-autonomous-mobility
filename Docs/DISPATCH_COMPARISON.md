# Inha Mobil 배차 정책 비교

2026-10-19 · 현재 checkout의 가상 시간 시연 범위. 실제 차량·센서·Physics 검증과 구분한다.

## 웹 사용

관제 `/demo/`의 **배차**에서 FIFO/Greedy/Hungarian을 선택한다. 이후 배차에만 적용하고 활성 임무/승객을 빼앗거나 경로를 바꾸지 않는다. 기본은 FIFO이며 초기화도 현재 선택한 배차/전역 탐색을 유지한다. A*/Dijkstra 선택과 배차 정책 선택은 독립이다.

상단 **배차 비교**(`/demo/comparison.html`)에서 다음 조건을 선택한다.

- 혼합 12건: 승객/화물과 마감 4건. 0초 6건, 180초 3건, 400초 3건.
- 캠퍼스 5개 목적지: 기존 확장 목적지 요청 5건을 동시에 접수한다.
- 하이테크 18건: 충전 대기/복귀를 포함한 기존 시나리오.
- 현재 시연의 요청: 취소를 제외한 접수 기록을 생성 시각 순서대로 재실행한다. 완료된 요청도 포함한다. 동일 시각만 하나의 batch다. 간격을 임의로 합치지 않으므로 온라인 단일 요청에서는 Greedy와 Hungarian이 같을 수 있다.

경로 탐색과 1/3/5회 반복을 지정해 비교한다. 반복은 알고리즘 실행 순서를 회전시킨다. 가상 결과와 차량 배정이 반복마다 일치하는지 검사하며 실제 계산시간만 달라질 수 있다. 결과 JSON에는 전체 요청 조건·초기 차량/배터리/거점·지도 파일 해시·비용 설정과 조건 SHA-256을 보존한다. 최대 60건, 5회다. 비교는 독립 서비스 인스턴스이며 관제 시계/차량/요청을 변경하지 않는다.

모든 정책은 설정의 같은 초기 차량/충전량과 자기 복귀 거점에서 시작한다. 현재 시연의 차량 위치·잔량을 복사하는 실험이 아니라 **같은 요청을 같은 초기 상태에서 재실행**하는 비교다. 기본 설정은 차량 3대, 30km/h, 2,000Wh 완충, Wh/m·충전기·15% 예비량 등 기존 합성 가정이다. 실제 통행·도로 폭·접근성 승인은 아니다.

## 알고리즘과 공통 제약

FIFO는 기존 `(created_s, id)` 요청 순서와 가용 차량 대기열 순서를 그대로 유지한다. 불가능한 요청은 대기시키고 가능한 다음 요청을 검사한다. 비용·요청 우선순위 최적화는 적용하지 않는다.

Greedy/Hungarian은 정원/화물/휠체어 슬롯, Stop 접근성, 도로/세 구간 경로와 왕복 에너지+15% 예비량을 먼저 검사한다. 실패한 조합은 매칭 후보에서 제외한다. 큰 비용으로 우회시키지 않는다. `available=true`라도 진행 중 임무가 있는 차량은 제외한다. 충전 중인 거점 차량도 왕복 에너지와 15% 예비량을 확보하면 후보에 포함한다. 실제 선택된 차량만 충전을 중단한다. 부족한 차량은 필요한 잔량에 도달하는 시점에 재평가하며 완충을 강제하지 않는다. FIFO는 기존 가용 차량 다음에 충전 시작 순서로 충전 차량을 고려하고, Greedy/Hungarian은 동일한 비용과 제약을 적용한다. 충전 기록의 completed는 세션 종료, interrupted는 배차에 의한 중단을 뜻한다.

요청 우선순위는 설계의 일반 승객 2/화물 1/이동지원 요구 3, 120초 aging, 마감 창 600초/가중치 2를 사용한다. 최선의 가능 픽업+운송 시간으로 slack을 계산하며 동률은 생성 시각→ID다. 장기 대기 600초 이상인 적합 요청이 있으면 매 세 번째 배차 기회에 가장 오래 기다린 적합 요청을 보호한다. Hungarian batch에 이 기회가 포함되면 그 요청을 먼저 매칭 가능한 요청 집합에 포함한다. 조건이 불가능한 요청을 위해 차량 능력을 완화하지 않는다. 서비스 유형별 정식 공정성 실험/M5 전체 완료는 아니다.

공통 비용은 다음과 같다.

```text
J = 픽업 소요시간 + 0.5 * 운송 소요시간
    + 2 * 예상 지각시간
    + 전체 임무 Wh / 가상 충전기 W * 3600
    + 희소 차량 패널티
```

에너지를 충전 초로 환산하는 값은 실험 가정이며 실제 비용 모델이 아니다. 휠체어 요청이 대기할 때 일반 요청이 휠체어 지원 차량을 사용하면 120초 패널티를 적용한다. 실제 수행 가능 여부는 별도 Hard Constraint다. 미래 요청을 미리 보지 않으며 deadline은 soft 속성이다. 탑승/적재/재출발 소요시간은 기존 가상 시간 모델과 동일하게 미구현이다.

Greedy는 우선순위 요청별로 현재 적합 차량 중 최소 J를 즉시 고른다. Hungarian은 우선순위 순서로 augmenting matching이 가능한 요청 집합을 만들고, 그 집합의 차량-요청 비용 합을 자체 Hungarian으로 최소화한다. 단순히 상위 N건만 잘라 특정 차량에만 몰려 빈 차량이 남는 문제를 피한다. 높은 우선순위 요청을 가능한 한 보존하면서 최대 개수의 요청을 선택한다. 남은 요청은 대기한다.

선택된 요청 수≤유휴 차량 수인 직사각형 행렬을 사용한다. 불가능 조합은 `None`(존재하지 않는 간선)이며, 요청 집합은 완전한 row matching이 가능한 경우에만 추가한다. 따라서 dummy 큰 비용/가짜 불가능 배차가 필요 없다. 요청 1건이면 Greedy와 같은 최소 비용 선택이 된다. 입력 ID 정렬로 동률을 결정한다. 원 개념 출처는 [Kuhn의 assignment problem 논문](https://onlinelibrary.wiley.com/doi/10.1002/nav.3800020109)이며 런타임 외부 최적화 라이브러리는 추가하지 않았다.

Hungarian의 최적성은 **그 tick에 선택된 요청 집합과 비용 snapshot**에 한정한다. 미래 요청/충전/완료 후 거점 재배치까지 전역 최적화하지 않는다. 총 대기시간·거리·완료시간이 항상 Greedy보다 좋다고 주장하지 않는다.

## 일괄 접수와 이벤트 순서

`create_batch`는 모든 Stop 입력을 먼저 확인하고, 같은 시각에 모두 큐에 넣은 뒤 한 번 배차한다. 기존 시나리오 버튼도 이 경로를 사용한다. 일반 요청은 기존처럼 즉시 접수한다. 같은 시각의 임무 복귀/충전 완료와 기존 큐 처리를 새 도착 묶음보다 먼저 수행한다. 배터리/충전 완료와 귀환을 시간 순서로 처리하며 미래 요청을 앞당겨 보지 않는다.

비교는 마지막 도착 이후 귀환/충전 완료 이벤트까지 전진한다. 미배정 요청이 있고 미래 해제 이벤트가 없으면 멈추고 미배정으로 남긴다. 실패를 무한 대기나 가짜 완료로 숨기지 않는다. ID의 생성 순번은 원래 접수 순서를 보존한다.

## 지표 정의와 한계

| 지표 | 정의 |
|---|---|
| 배차 대기 | 임무 출발−요청 생성 |
| 픽업 대기 | 픽업 도착−요청 생성 |
| 전체 운송/복귀 완료 | 비교 시계 기준 마지막 dropoff/return. 마지막 충전 종료와 구분 |
| 이동/공차 거리 | 픽업+운송+복귀 / 픽업+복귀 |
| 에너지/충전 | 기존 합성 에너지 전체 임무 합 / 충전 시작 횟수 |
| 마감 내 완료율 | 마감이 있는 전체 요청 중 마감 이내 완료 비율. 미배정도 실패에 포함 |
| 계산 p50/p95 | 경로·제약 평가와 매칭을 포함하는 배차 호출 시간. 실행 가능한 유휴 차량/대기 요청이 있는 호출의 표본 |
| 비용 J 합계 | 실제 선택된 조합의 비용 합. 서로 다른 시각의 선택을 포함하므로 전체 최적성 증명이 아님 |

대기/픽업 통계는 배정된 요청에 한정하고 완료/미배정을 항상 함께 표시한다. 값이 없으면 null/—다. p50/p95는 nearest rank다. 1/3/5회는 PC 시연용 반복이며 통계적 유의성이나 기준 장비의 성능 목표 달성 검증은 아니다. 비교 스레드와 관제가 CPU를 공유하므로 계산 시간에 영향을 줄 수 있다. 소수의 기본 시나리오를 일반화하지 않는다. 승객 탑승, 장애물, 교통, 재배차, 만료, Reservation/CBS, 수요 재배치는 포함하지 않는다.

### 인지한 비교 한계: 차량 간 경합

2026-10-19 사용자 지적으로 기록한다. 현재 지표에는 동일 차로의 추종 지연, 단일 차로 대향 차량의 양보, 교차로/합류부 예약 대기가 포함되지 않는다. 방향 간선이 따로 존재해도 물리적 차선 분리가 확인된 것은 아니다. 공유 구간 예약과 센서 기반 안전거리 처리는 후속 검토 항목이며 이번에는 구현하지 않는다. 상세 인지 내용은 [구현 현황](implementation_status.md#인지한-미구현-사항-차량-간-경로-충돌)에 기록한다. 해당 계층을 구현하면 세 배차 정책 모두 같은 경합 제약 아래 재비교해야 한다.

## 검증

Python 개발 환경과 `backend/src`를 PYTHONPATH에 둔다.

```powershell
python -m pytest backend/tests -q
python scripts/compare_dispatch.py --source mixed --planner astar --repeats 3
```

전체 backend 187개 통과(기존 Starlette TestClient deprecation 경고 1개). 작은 무작위 직사각형/금지 간선 행렬 25개는 모든 순열의 정답과 대조했다. Greedy 비용 101 대 Hungarian 4인 반례, 부분 매칭, 장기 대기 보호, 용량/점유/통행 Hard Constraint, batch 사전 검증, 반복 재현과 독립 API를 확인했다. Ruff 검사/format check 및 JS 세 파일 구문 검사를 통과했다. Unity 컴파일/센서/Physics/실차 성능은 검증하지 않았다.

사용자 제공 PNG를 원본 그대로 `web/inha-mobil-icon.png`에 포함해 관제·비교·RRT/TTC 헤더/파비콘에 적용한다. 기존 SVG 기능 아이콘은 유지한다. 이미지 저작권·라이선스를 임의로 새로 선언하지 않는다.
